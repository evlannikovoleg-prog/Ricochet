# XGBoost-ранжирование кандидатов

Модуль `src/ricochet/ranking/` — изолированная надстройка над статистическим
движком. `leadlag.py` по-прежнему отвечает только за чистую статистику: бининг,
lag-корреляции, устойчивость и вердикты. Ранжировщик не меняет эти расчёты, а
получает уже готовые пары и решает, какие из них достойны внимания инженера и
ИИ-агента.

## Зачем отдельный слой

Движок намеренно находит широкий слой кандидатов: после контролей на реальном
снимке остаётся 258 пар. Отправлять их все в LLM или дежурному инженеру — значит
порождать «шторм аномалий». XGBoost выступает жёстким ренчером:

- сортирует пары по вероятности истинной зависимости;
- позволяет безопасно снизить `min_devices` до 2 и не захлебнуться в ложных
  корреляциях;
- учится на локальной обратной связи конкретного контура («Классная находка» /
  «Это спам»), а не требует переписывать статистические формулы под каждую
  компанию.

Ключевое архитектурное правило: **модуль ранжирования зависит от движка, но
движок не зависит от ранжировщика**. Это сохраняет математическое ядро
проверяемым и заменяемым.

## Пайплайн

```text
alarms.parquet
      │
      ▼
run_butterfly() + finalize_pairs()          ← ядро, без изменений
      │  pairs: corr, lead, lag, support, days, regions, overlap, class...
      ▼
ranking.PairFeatureContext.build()          ← lift, topология, degree по авариям
      │
      ▼
ranking.PairRanker.score_pairs()
      │  XGBoost (если обучен) или heuristic-v1 (cold start)
      ▼
pairs[*].xgboost = {probability, decision, rank, model_kind, features...}
      │
      ├── GET /api/v1/butterfly/pairs     ← отсортировано по вероятности
      └── POST /api/v1/precheck/incident  ← только топ-5 с порогом 0.9
```

## Признаки

Модель получает 35 чисел. Они сгруппированы по смыслу:

| группа | признаки |
|---|---|
| корреляция и лид | `corr_abs`, `corr_signed`, `corr0_abs`, `lead`, `lead_ratio`, `lag_abs_min`, `lag_is_zero` |
| объём и устойчивость | `support_log`, `days_frac`, `days_total_log`, `regions_frac`, `month_stable`, `holdout_ok`, `score_engine` |
| активность рядов | `duty_max`, `duty_min`, `device_min_log`, `device_max_log`, `device_ratio` |
| вердикт по устройствам | `class_butterfly`, `class_duplicate`, `class_cross_object`, `class_ambiguous`, `overlap_frac`, `common_devices_log`, `corr_shared_abs`, `corr_unshared_abs` |
| межсистемность | `same_integration`, `same_system` |
| lift и топология | `graph_degree_log`, `cooccurrence_lift_log`, `temporal_jaccard`, `topology_site_affinity`, `topology_token_jaccard`, `topology_region_affinity` |

`cooccurrence_lift` считается по бинам: во сколько раз совместная активность
пары выше произведения маргинальных активностей. `temporal_jaccard` — доля
общих активных бинов. Топология извлекается из `node`/`node_alias`:

- `topology_site_affinity` — совпадение доменных суффиксов (`*.msk`, `*.spb`);
- `topology_token_jaccard` — пересечение нормализованных токенов имён
  (цифры заменяются на `#`, чтобы `ape001.msk` и `jmx002.msk` давали общий сайт);
- `topology_region_affinity` — пересечение распределений регионов.

Пропуски передаются в XGBoost как `NaN`: модель отличает «признак неизвестен»
от «признак равен нулю». Порядок `FEATURE_NAMES` — контракт сохранённой модели;
менять его можно только вместе с переобучением.

## Cold start и обучение на обратной связи

Пока модель не обучена, ранжировщик работает в режиме `heuristic-v1`:
прозрачная формула по корреляции, лиду, устойчивости, lift, топологии и
штрафам за дублирование. Это позволяет сервису работать с первого запуска и не
блокирует предпроверку.

Обратная связь:

1. UI/инженер вызывает `POST /api/v1/ranker/feedback` с `pair_id` и меткой
   `good` или `spam`.
2. `FeedbackStore` сохраняет метку и **снимок признаков** в
   `state/ranker_feedback.json`. Снимок нужен, чтобы пересборка графа не
   ломала обучающую выборку.
3. После `min_train_samples=20` записей и минимум `2` примеров каждого класса
   модель обучается автоматически; повторное обучение — каждые 10 новых меток.
4. Модель и метаданные атомарно сохраняются в `state/ranker_model.json` и
   `state/ranker_model.meta.json`.
5. `GET /api/v1/ranker/status` показывает версию модели, метрики и важность
   признаков.

Ручное обучение:

```powershell
python scripts\train_ranker.py --force
# или
curl.exe -X POST http://127.0.0.1:8077/api/v1/ranker/train `
  -H "Content-Type: application/json" -d "{\"force\":true}"
```

Метрики обучения (`auc`, `accuracy`, `high_confidence`) считаются на той же
выборке и служат диагностикой, а не доказательством качества. Для честной
оценки нужен отложенный набор инцидентов; до его появления решения модели
должны проходить экспертную проверку.

## Порог и предпроверка

По умолчанию:

- `min_confidence = 0.9` — пара считается «прошедшей»;
- `review_confidence = 0.5` — серая зона;
- `precheck_top_k = 5`.

`POST /api/v1/precheck/incident` получает только топ-5 пар с вероятностью
выше порога. Предпроверка пересчитывает вероятности текущей моделью на лету,
поэтому после дообучения не нужно ждать нового прогона графа. Если ни одна
пара порог не прошла (молодая модель, редкий контур),
включается явный `fallback`: лучшие пары по рангу всё равно попадают в
предпроверку, а в ответе `case["ranker"]` стоит `fallback=true`. Это защищает
инцидент от «пустого дела», но не скрывает факт холодного старта.

## Снижение min_devices до 2

Рабочий сценарий:

```json
{
  "min_devices": 2,
  "min_abs_corr": 0.35,
  "holdout_last": 1
}
```

Движок находит больше пар, в том числе на двух устройствах. Ранжировщик
отсекает те, у которых нет lift, топологической близости и устойчивости.
Статистические пороги при этом не переписываются: расширение воронки и её
сужение разделены по ответственности.

## Ограничения

- XGBoost не заменяет ground truth. При малом числе меток вероятности смещены,
  а метрики обучения оптимистичны.
- Обратная связь субъективна; для продакшена нужны правила разметки и
  контроль доли спама.
- Модель обучается на парах текущего графа. При смене набора метрик или
  семантики `alert_group` нужен период накопления новой обратной связи.
- `FeedbackStore` — локальный JSON, без транзакций и версионирования. Для
  нескольких воркеров нужна общая БД/очередь.
- Топология в текущей реализации — эвристика по именам узлов и регионам.
  При наличии CMDB следует заменить её на расстояние в графе сети.
